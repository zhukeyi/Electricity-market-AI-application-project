## 2 每日提交前（BJ 23:00 定时器跑完后）

| # | 检查项 | 命令 / 位置 |
|---|---|---|
| 1 | 运行日是否为**明天** | `runs/<日期>.json` 的 `schedule` 字段，`rolled` 应为 0 |
| 2 | preflight 是否报警 | 队名占位符 / 非默认运行日 / DST 日 |
| 3 | fetch 后数据是否覆盖到 D−1 | `last_date` 应 ≥ D−1 |
| 4 | optimize 是否 ok | 若 abort，看 detail 里的 SOC 越界方向 |
| 5 | verify 是否通过 | 24 行 / 1 天 / 结构校验 / SOC 链重放 |
| 6 | SOC 末态是否在 [0.7, 13.3] | 在界内即可，不要求「留余量」 |
| 7 | 是否出现 ±0.01 的补偿动作 | 若出现属正常（死区被正确回退），不要手动改 |

```bash
./scripts/sync.sh status     # 定时器 + 最近一次运行摘要
./scripts/sync.sh down       # 拉回提交文件
```

## 3 每日提交操作

| 步骤 | 操作 | 注意 |
|---|---|---|
| 1 | 从 `data/out/submission/<日期>/` 取 CSV | **只取当天的目录**，不要取错 |
| 2 | 核对文件名中的队名 | `（USTC管理学院_线上组_交易决策）AI+电力市场应用大赛结果提交.csv` |
| 3 | 上传到比赛平台 | 窗口：BJ D−1 10:00 → D 02:00 |
| 4 | 确认平台解析出 24 行 | 若平台显示行数异常，立即排查字节规格 |
| 5 | 记录上传回执 | 截图或日志，便于赛后复盘 |

### 3.1 「先保底、后覆盖」策略

手册允许以最后一次为准。风险结构因此对我们有利：

```
① 定时器 BJ 23:00 生成文件
② 立即上传（此时距截止还有 3 小时）
③ 确认平台已正确接收
④ 若有时间，可再优化覆盖；若无时间，已有一份可行解在手
```

**绝不要等到 01:30 才第一次上传。**

## 5 绝对不要做的事

| 禁止 | 原因 |
|---|---|
| 照抄官方模板的示例曲线 | HR17–19 为 +10 MW，超 Pmax 且 SOC 穿底至 −157%，当日归零 |
| 把优化器降级为 LP | LP 允许同时充放，会造出「模型认为可行、实际穿底」的曲线 |
| 用逐时段独立截断做量化 | 相邻时段舍入方向相反会使 SOC 轨迹断裂 |
| 设预测收益门槛 / 价差过滤 / 缩量 | 三者均已用 681 天数据证伪为净亏 |
| 手工修改生成的 CSV | 任何手改都可能破坏字节规格（BOM/CRLF/两位小数） |
| 等到最后一小时才上传 | 无重试窗口；且平台解析异常时来不及修 |
| 用「只重放前一日文件」推初始 SOC | 初始 SOC 会逐日漂移，从某天起每天 abort |
| 忽略 preflight 的告警 | 告警是精确设计的，忽略它会训练出「忽略告警」的习惯 |

## 6 故障应急

| 症状 | 首查 | 处置 |
|---|---|---|
| preflight ✗ | 运行日是否已过期 / 是否 DST 日 | 用 `--date` 指定正确运行日；DST 日不可提交 |
| fetch 失败但数据落后 ≤ 3 天 | 网络 / CAISO 接口 | 降级继续，事后补数 |
| fetch 失败且落后 > 3 天 | Oracle 出口 / OASIS 接口变更 | 手工核实，必要时改用 SSH 代理传输 |
| optimize abort（SOC 越下限/上限） | 昨日的 SOC 末态 / 数据是否有半天 | `chain_soc` 是否退回单日重放；补全数据 |
| verify ✗（行数/结构） | 写入端字节规格 | 不要手改，重跑 `--force` |
| 数据体检报「N 个时段」 | 该日 DAM 是否尚未出清完 | 若为当日半天数据，等出清后重跑 |

### 6.1 手工补跑

```bash
python scripts/pipeline.py --date 2026-11-24 --force --allow-late
```

`--allow-late` 会放过「截止已过」，但**不会放过 DST 日**——这是刻意的。
