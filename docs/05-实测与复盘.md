# 05 实测与复盘

> 所有数字来自真实 CAISO SP15 历史价格回放，不是模拟数据生成的。
> 回测方式：逐日滚动——用截至 D−1 的数据预测 D，按 D 的真实价格结算，SOC 链连续传递。

## 1 赛前彩排（2026-11-20 执行）

**环境**：Oracle ARM `217.142.246.70`（唯一可直连 CAISO 的节点）｜队名 USTC管理学院｜手册 V3.0

### 1.1 赛期首日结构性彩跑（运行日 2026-11-23）

```
preflight  ! 运行日非默认（默认 2026-11-21，本次 2026-11-23，差 +2 天）
fetch      ! direct +16 行 → 至 2026-11-20（仍缺至 11-22，CAISO 尚未发布）
forecast   ✓ 预测·blend｜1052 天历史｜价 0.3~42.2 均值 27.4
optimize   ✓ SOC 0.700→0.707（赛期首日，按手册 SOC0=5%，忽略赛前预演历史）
             充 14.79 / 放 10.68 MWh｜预期 $427.65｜6/24 段有动作
write      ✓ （USTC管理学院_线上组_交易决策）…csv（2333 字节）
verify     ! 24 行 / 1 天｜通过｜模板待核实 4 项
```

两条告警均属**预期**，非故障：

1. 运行日非默认 —— 彩排指定了 11-23，自然运行日是 11-21，preflight 按设计提醒。
2. 数据缺至 11-22 —— 11-21/11-22 的 DAM 尚未出清（分别在北京时间 11-21 02:00、11-22 02:00 出清）。真实运行时（11-22 23:00 触发）数据会补齐。

> 预期收益 $427.65 是基于未出清价格的结构性推算，不构成收益预期。

### 1.2 文件字节核验

```
字节数 2333 ｜ CRLF 27 处 ｜ 说明行内裸 LF 3 处
标题：（线上组）USTC管理学院 (团队成员甲\乙)——交易决策结果,,,,,

HR17：17,2026/11/23,17,2026-11-24T00:00:00-00:00,2026-11-24T01:00:00-00:00,0.00
末行：24,2026/11/23,24,2026-11-24T07:00:00-00:00,2026-11-24T08:00:00-00:00,6.99
```

两个值得说明的细节：

- **HR17 的 GMT 已进入 11-24，而 `OPR_DT` 仍为 2026/11/23** —— 符合模板跨日特征，不能按 GMT 日期分组。
- **HR1 的 `-0.01` 是有意的微量补偿**：末段放电后若不能回补 0.0017 MWh，SOC 会跌破 5% 下限。死区归零（把 ±0.01 归零）因此被正确地**回退**。

### 2.1 最弱日 11-19（51.3%）的复盘

相关 0.859 并不算差，但**价差结构被误判**，充放时段错位。

这是本方案最典型的失败模式：**不是价格水平错，而是价格形态错**。相关 0.86 说明整体涨落方向抓对了，但「哪个小时最贵、哪个小时最便宜」这个排序错了，而套利收益完全取决于排序。

关键判断：**这类损失无法通过「跳过整日」规避**。681 天实验已证明任何预测收益门槛都是净亏（详见 `03-策略与思路.md` §4.2），因为 11-19 这类日子的预测预期收益往往并不低。

**合计收益随门槛单调下降；负收益日只减少 11 天；最差日改善 $51，代价 $1,597。**

结论：门槛挡不住亏损日，只挡住盈利日。原因见 `03-策略与思路.md` §4.2。

### 3.2 负收益日的统计特征

| 项目 | 数值 |
|---|---|
| 负收益日占比 | **4.5%**（31/681） |
| 单日最差 | **−$167**（约为日均收益的 0.46 倍） |
| 典型反例 | 2026-10-11：预期 $472（当年最高之一），实际 **−$19** |

成因：预测把充放时段排错，而实际价差又不小，`η² = 0.7225` 下 **38% 的保本价差**被击穿。

> 保本条件：`p_d / p_c > 1/η² = 1.384`。价差 38.4% 以上才赚钱。时段排错时，实际执行的组合往往跨不过这条线。

### 3.3 其他方案的对照

| 方案 | 实测 | 判定 |
|---|---|---|
| 价差过滤（阈值 $20） | 捕获率 96.4% → **71.5%** | 禁用 |

## 4 失败模式与代价

| 失败模式 | 后果 | 量级 | 可恢复性 |
|---|---|---|---|
| 某天预测偏、收益低（如 11-19） | 单日少赚，其余日照常 | 可承受，天然波动 | 自动恢复 |
| 某天漏交 / 越限 / 格式错 | 当日 `R=0` | **−7.1%**（1/14） | 单日损失，次日恢复 |
| **连续多天失败** | 每天 `R=0` | 3 天 = **−21%** | **不可逆** |

**越限与漏交后果完全相同**——都是当日归零。所以「保证物理可行」的价值不在于「避免 0 分」，而在于「避免从正值掉到 0」。

而第三行才是灾难。它的成因从来不是模型不准，而是**故障通过状态变量跨日传播**。

## 5 案例复盘：一次真实的跨日传染

### 5.1 现象

Oracle 定时器连续 3 天运行失败：

| 运行日 | 结果 | 六步 |
|---|---|---|
| 11-15 | ok=True，$401.99 | preflight✓ fetch✓ forecast✓ optimize✓ write✓ verify✓ |
| 11-16 | ok=True，$402.42 | 同上 |
| 11-17 | ok=True，$337.54 | 同上 |
| **11-18** | **ok=False** | **preflight✗** |
| **11-19** | **ok=False** | preflight✓ fetch✓ forecast✓ **optimize✗ abort✗** |
| **11-20** | **ok=False** | preflight✓ fetch✓ forecast✓ **optimize✗ abort✗** |

### 5.2 定位

`optimize` 报的是 SOC 越下限。重放历史文件后发现：

```
11-19 初始 SOC = 0.698294 MWh（程序认为）
真实值         = 0.710176 MWh
下限           = 0.700000 MWh
```

0.698294 < 0.7 → 直接 abort。

### 5.3 根因

`chain_soc(prev_file, soc_init)` 只重放**前一日**的提交文件，却把 `soc_init`（首日 0.7）当起点。

这是逻辑错误：**单日文件是从前一日的末态起算的，不是从首日起算的。**

```
错误逻辑：SOC₀(11-19) = replay(11-18 文件, 起点=0.7)
正确逻辑：SOC₀(11-19) = replay(11-15→11-16→11-17→11-18 全部文件, 起点=0.7)
```

前者丢掉了 11-15 ~ 11-17 三天的净充放。

### 5.4 为什么它比「某天亏钱」危险得多

| 特性 | 说明 |
|---|---|
| **不自我修复** | 每天的错误都从同一个错误起点衍生，误差持续累积 |
| **报告为「成功」** | 单看某一天的日志，一切正常 |
| **发现得太晚** | 只有在 optimize 真的越界时才暴露，此时已连败 3 天 |

如果这个缺陷带到赛期 14 天，会从第一个净 SOC 为负的日子开始**全线归零**——损失不是 7.1%，而是 21% 甚至 100%。

### 5.5 修复

```python
def history_submissions(outdir, trade_date, max_lookback=30, team=None):
    """收集赛期内、trade_date 之前的全部提交文件，按日期升序。"""
    ...

def chain_soc(prev_files, soc_init):
    """从首日起链式重放全部历史。"""
    soc = soc_init
    for f in prev_files:
        _, data, _ = read_submission(f, allow_legacy=True)
        for _, q in data:
            soc = replay_soc(q, soc)[-1]
    return soc
```

配套三条加固：

1. **同日多文件按队名去重**（避免旧队名文件混入链）。
2. **0.02 MWh 容差钳制**（`clamp_soc`）：舍入漂移导致的微小越界不应让当日 abort。
3. **强制赛期首日取手册 SOC₀=5%**，且**剔除赛前预演文件**（`>= DEFAULT_MARKET.contest_start` 过滤，仅作用于赛期内，不影响赛前预演）。

修复后用真实历史文件验证：初始 SOC 从错误的 0.698294 恢复为 **0.710176**。

### 5.6 教训

> 风险管理的第一优先级不是压低单日波动，而是**切断故障的跨日传播**。
>
> 单日失误是 7.1% 的可承受成本；连续失误是结构性的、无法补救的。

落到可执行的三条纪律：

1. **每条曲线必须过物理复算**（不能靠优化器自证），因为越限 = 漏交。
2. **任何跨日状态必须可重放、可钳制、可报警**，超容差不许静默。
3. **不做任何「为了安全」的收益折让**——价差过滤、收益门槛、缩量，三者都已用 681 天数据证伪。

### 6.1 数据体检的一个坑

早期实现按 `cnt < 24` 判定异常，结果把 23 段的 DST 切换日报成「仅 23 个时段（DST 当日应为 23）」——自相矛盾的告警。

修正为与 `la_day_hours(d)` 比较后，只报真异常（如 16 段 = 抓取窗口被截断）。**告警必须精确，否则会训练出「忽略告警」的习惯**，而这在赛期是致命的。
