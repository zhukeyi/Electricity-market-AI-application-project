# 04 工程实现

> 代码在本仓库可直接运行。本章说明为什么这样搭，以及哪些地方是「不能改」的硬约束。

## 1 架构：为什么算法跑在远端

本机出口**无法访问 `oasis.caiso.com`**（HTTP 000 / DNS SERVFAIL）。而 Oracle ARM 节点 `217.142.246.70` 可直连。

因此采取「本地开发 + 远端执行」：

```
本地（macOS）                          远端（Oracle ARM, Ubuntu 24.04）
─────────────                          ─────────────────────────────
写代码 / 跑单测                          systemd timer  BJ 23:00 触发
  │                                       └─ daily.sh（钉死运行日 + 重试 3 次）
  └── scripts/sync.sh up ──────────────►      └─ pipeline.py 六步
                                                   ├─ 抓 CAISO OASIS
                                                   ├─ 预测 → 优化 → 写盘
                                                   └─ 自检 → 记账
      ◄───────── scripts/sync.sh down ────────────┘
      拉回提交文件（手工上传平台前必做）
```

两端依赖版本完全锁死（`requirements.txt`）：`numpy==2.5.4` / `pandas==3.1.1` / `scipy==1.18.1`。同一份代码在两端跑出**逐字节相同**的提交文件，这一点已在实跑中验证。

> 为什么不用 `requests`：`src/caiso/client.py` 只用标准库 `urllib.request`，为 Oracle 减少一个依赖。

## 3 流水线：八步

```
15:00 UTC（= BJ 23:00）systemd timer 触发
  └─ scripts/daily.sh  →  钉死运行日 = LA 明天，失败重试 3 次（间隔 5/10 分钟）
       └─ scripts/pipeline.py
            ① preflight  截止时间 / DST 日 / 赛期 / 队名占位符 检查
            ② fetch      增量抓数（direct / ssh 自动选路；失败可容忍落后 3 天）
            ③ forecast   blend（0.4×昨日 + 0.6×近 7 日中位）
            ④ optimize   MILP → 量化 → 死区清理 → 可行性复核
            ⑤ write      按模板字节规格落盘
            ⑥ verify     回读 + 结构校验 + SOC 链式重放
            ⑦ record     data/out/runs/<日期>.json 与 log.jsonl
            ⑧ notify     可选 webhook（企业微信/钉钉）
```

### 3.1 为什么是 BJ 23:00

截止是 BJ D 日 02:00。BJ 23:00 触发意味着**留 3 小时缓冲**，且此时 LA D−1 日 07:00，CAISO 已发布 D−1 日的出清结果（前一日 13:00 发布），数据是完整的。

若触发太晚（如 BJ 01:00），一旦抓数或优化出错，重试窗口不足；若太早，D−1 日数据可能还没入库。

### 3.2 失败容忍

| 情形 | 行为 |
|---|---|
| 抓数失败但本地数据落后 ≤ 3 天 | **降级继续**（`warn=True`），用陈旧数据预测 |
| 落后 > 3 天 | **致命**，`raise PipelineError`，不进 optimize |
| optimize 不可行 | 比例收缩保底；仍不可行则 abort |
| 文件已存在 | 复用，不覆盖（`--force` 才重写） |

> `max_stale_days=0` 会让链路被任意瞬时网络故障打死，所以默认 3 天。但 3 天是权衡值，不是安全值——**陈旧数据会让预测质量下降**，preflight 会明确报出落后天数。

## 4 五道防线：为什么不能省任何一道

可行性是二元的。为了让「越限」的概率压到工程上可忽略，串行设五道：

| 序号 | 防线 | 作用 |
|---|---|---|
| 1 | **MILP 充放互斥** | 从建模层消除「同时充放」这一物理不可实现的解 |
| 2 | **`quantize_feasible`** | 把连续解量化到两位小数时，在 **SOC 空间**前向修复，而非逐时段截断 |
| 3 | **`replay_soc` + `validate_dispatch`** | **独立于优化器的第二实现**，逐时段重算 SOC 轨迹并校验 |
| 4 | **`apply_deadband`** | 把微量动作归零，使曲线干净；归零后若不可行则**回退** |
| 5 | **`repair_to_feasible`** | 整体不可行时按比例收缩全部动作，直至可行（保底不归零） |

### 4.1 为什么必须是 MILP 而不是 LP

LP 松弛允许同一时段同时充放（`Qc>0` 且 `Qd>0`）。这在物理上不可能，但线性模型不禁止。

两者对 SOC 的影响差多少？设该时段充 `Qc`、放 `Qd`：

```
线性模型认为：ΔSOC = Qc − Qd
真实物理值为：ΔSOC = 0.85·Qc − Qd/0.85
差值      ：  0.15·Qc + 0.1765·Qd
```

取 `Qd = Qc = k`：**线性模型认为 SOC 不变，真实却下降 `0.3265·k` MWh。**

具体例子：`Qc = Qd = 3 MW`，`SOC₀ = 0.75 MWh`（贴下限）。

| | SOC 末态 | 判定 |
|---|---|---|
| LP 认为 | 0.75（不变） | 未破下限，**可行** |
| 真实 | 0.75 − 0.98 = **−0.23** | **严重越界** |

一条「模型认为贴在下限内、实际穿底到负值」的曲线，交上去就是全天归零。

**所以 `use_milp=True` 是硬性要求。** LP 只能用于快速探索，绝不能用于出提交件。

### 4.2 为什么量化必须在 SOC 空间做

朴素的「逐时段四舍五入到两位小数」有个隐蔽问题：相邻时段的舍入方向相反时，SOC 轨迹会断裂。

例：t 段充 → 向上舍入使 SOC 多涨；t+1 段放 → 向下舍入使 SOC 少跌。两段单独看都在界内，累积起来就出去了。

`quantize_feasible` 的做法是**前向修复**：逐时段量化后，重新计算 SOC；若该步使 SOC 越界，就把这一步的动作向可行方向钳到刚好可行为止（`_quantize_floor` 保证向零方向量化，即「放电少放、充电少充」）。

`round_conservative` 作为旧接口保留，**仅供对照**，不得用于提交。

### 4.3 为什么校验器必须是独立实现

如果校验器和优化器共用同一份 SOC 递推代码，那么代码里的一个符号错误会同时骗过两边——优化器认为可行，校验器也认为可行。

`validate/feasibility.py` 独立重写递推式，只依赖 `params.py` 的常数。这是刻意的冗余。

**实证价值**：官方示例曲线的不可行性，正是被这个独立校验器抓出来的（优化器根本不会产出那种曲线）。

## 5 时序模块：三时间轴与「可提交性前滚」

### 5.1 三个时区

`pipeline/clock.py` 维护 `LA` / `BJ` / `UTC` 三个 `ZoneInfo`，所有时间换算走它，不在业务代码里手算。

关键常量：

```
运行日 D 的截止 = BJ D 日 02:00
                = LA D−1 日 10:00
                = UTC D−1 日 18:00
```

### 5.2 一个真实踩到的坑：`LA 今天+1` 不等于「该提交哪天」

最初实现按 `trade_date = la_today() + 1` 算运行日。这在定时器 BJ 23:00 触发时是对的（LA 当天 07:00 → +1 = 明天，截止在 3 小时后）。

但**手工在 BJ 白天触发时就错了**：此时 BJ 已是 D 日上午，D 日的截止（BJ D 02:00）**已经过去十几小时**。链路会兴冲冲地生成一份已经过期、永远交不上去的文件。

修复方式是引入 `next_submittable()` 前滚：

```python
def next_submittable(now=None, max_roll=2):
    base = la_today(now) + 1 day
    for roll in range(max_roll + 1):
        cand = base + roll days
        if bj_deadline(cand) > now:      # 这一天的闸还没关
            return cand, roll
    return base + max_roll, max_roll
```

同时 preflight 对**任何非默认运行日**报警（`warn=True`），`Schedule.rolled` 记录前滚了几步。

> 这个缺陷是自己在激活定时器后手工触发时发现的，不是线上反馈。它属于「静默生成无效产物」类缺陷——最危险的一类，因为流水线会报「成功」。

### 5.3 DST 日

`la_day_hours(day)` 用 zoneinfo 实算洛杉矶当日实际小时数：

```python
start = datetime.combine(day, time(0,0), tzinfo=LA)
end   = datetime.combine(day + 1 day, time(0,0), tzinfo=LA)
return round((end.astimezone(UTC) - start.astimezone(UTC)).total_seconds() / 3600)
```

2026 年美国夏令时：3-08 起（23 小时日）、11-01 止（25 小时日）。赛期全程 24 小时，但代码**不依赖这个巧合**——preflight 会拒绝非 24 段的日子（即使 `--allow-late`）。

数据体检同理：只报「与 `la_day_hours(d)` 不符」的日子。修复前的实现按 `< 24` 判定，把 23 段的 DST 日报成「仅 23 个时段（DST 当日应为 23）」这种自相矛盾的告警，制造告警疲劳。

## 6 提交文件的字节级写入

规格见 [`02-规则详解.md` §7](02-规则详解.md#7-提交文件规格由官方模板反解--字节级核验)。实现要点：

| 要点 | 实现 |
|---|---|
| BOM 位置 | 文件头**不加** BOM；表头第二列前**加** `\ufeff` |
| 行尾 | 27 处 CRLF；说明行内部 3 处裸 LF |
| 小时格式 | `1..24`，不补零 |
| 日期 | `yyyy/m/d`，月日不补零 |
| GMT 偏移 | 字面量 `-00:00`（不是 `+00:00`、不是 `Z`） |
| GMT 时刻 | 由 `interval_gmt(date, hour)` 用 zoneinfo 实算，不硬编码偏移 |
| 回读校验 | `read_submission()` 交叉校验 GMT 列与 `OPR_DT`/`OPR_HR` 是否自洽 |

### 6.1 回读交叉校验的意义

如果写入端把时区算错（比如用了 PST 而非 PDT 的偏移），文件本身语法完全合法，平台也会照单接收——但 24 个时段的价格会整体错位 1 小时。

`read_submission()` 因此做**双向一致性校验**：从 `OPR_DT` + `OPR_HR` 重新独立算出应有的 GMT 区间字符串，与文件中的两列逐字比对。不一致就抛错。

### 6.2 旧格式兼容通道

赛前预演产生的历史文件是旧 4 列格式。新的严格读取器会拒收它们，导致 SOC 链在 11-18 处断掉。

处理方式：`read_submission(..., allow_legacy=True)` 仅供**内部历史重放**使用；**提交前自检仍严格拒收旧格式**。这条边界必须守住——否则一次误配就可能让旧格式文件混进正式提交。

## 7 部署与运维

```bash
# 本地改完代码后上行（含依赖版本锁）
./scripts/sync.sh up

# 首次部署：连数据一起播种，然后在 Oracle 上装 systemd 单元
./scripts/sync.sh up --with-data
ssh -i ~/.ssh/id_rsa_oracle ubuntu@217.142.246.70 'bash ~/csg-ai-market/deploy/install.sh'

./scripts/sync.sh status      # 定时器状态 + 最近一次运行摘要
./scripts/sync.sh down        # 拉回结果与数据（手工上传平台前必做）
```

### 7.1 systemd 单元

```ini
# deploy/csg-pipeline.service / .timer
OnCalendar=*-*-* 15:00:00 UTC
Persistent=true
RandomizedDelaySec=60
Restart=on-failure
```

- `Persistent=true`：机器重启后补偿错过的触发。
- `RandomizedDelaySec=60`：避免与系统其他任务同秒竞争。
- `daily.sh` 里 `rc=1` **按成功返回**，避免 systemd 循环重启。

### 7.2 配置

`.pipeline.env`（见 `.pipeline.env.example`）：

```
CSG_TEAM=USTC管理学院
CSG_MEMBERS=成员甲,成员乙        # 顿号/逗号分隔，自动转成「甲\乙」
CSG_METHOD=blend
```

**队名会进入提交文件标题，配错等于全部作废。** 若检测到 `xxxx队` 或 `测试队` 之类占位符，preflight 会报警。

### 7.3 手工补跑

```bash
python scripts/pipeline.py --date 2026-11-24 --force --allow-late
python scripts/pipeline.py --check-data          # 只做数据体检
```

## 9 三条不可违背的规则

1. **提交只能走 `prepare_submission()`**——它串起「求解 → 量化 → 校验 → 修复」，绕过任一步即可能归零。
2. **优化器必须用 MILP**（`use_milp=True`）——理由见 §4.1。
3. **SOC 量化不能用逐时段独立截断**——必须用 `quantize_feasible` 做 SOC 空间前向修复，理由见 §4.2。
